# زمان‌بندی خودکار دروس

وب‌اپلیکیشن کامل: کاربر فایل اکسل داده‌ها را آپلود می‌کند، برنامه داده
را می‌خواند و اعتبارسنجی می‌کند، یک مدل بهینه‌سازیِ واقعی (نه فقط
دمو) روی آن اجرا می‌شود و نتیجه به‌صورت جدول قابل‌خواندن + فایل اکسل
قابل‌دانلود نمایش داده می‌شود.

## ساختار پروژه

```
backend/
  app/
    core/config.py       تنظیمات مرکزی (نام شیت‌ها، حداکثر حجم فایل)
    models/schemas.py    قرارداد داده بین «خواندن اکسل» و «حل مدل»
    services/excel_reader.py   خواندن و اعتبارسنجی فایل اکسل
    solvers/base.py      رابط استاندارد و پلاگین‌پذیر برای هر solver
    solvers/cp_sat_solver.py   مدل بهینه‌سازیِ واقعی (OR-Tools CP-SAT)
    solvers/dummy_solver.py    نسخه‌ی خیلی ساده‌ی قبلی — دیگر استفاده نمی‌شود، فقط به‌عنوان مرجع مانده
    api/schedule.py      مسیرهای API: آپلود / حل / دانلود
    main.py               نقطه‌ی ورود FastAPI
frontend/
  src/
    components/TimetableGrid.jsx   عنصر بصری شاخص (گرید زمان‌بندی متحرک)
    components/UploadZone.jsx      ناحیه‌ی آپلود فایل (drag & drop)
    components/ResultsTable.jsx    جدول نمایش نتیجه
    api.js                          ارتباط با بک‌اند
    App.jsx                         جریان کلی صفحه
```

## مدل بهینه‌سازی

کد اصلیِ مدل (که قرار بود از همکار دریافت شود) در نهایت در دسترس قرار
نگرفت، پس یک مدل واقعی خودمان با **OR-Tools CP-SAT** نوشتیم
(`app/solvers/cp_sat_solver.py`) که این قوانین را رعایت می‌کند:

**محدودیت‌های سخت (هرگز نقض نمی‌شوند):**
- هر ارائه‌ی درس به «تعداد گروه درسی» پاره‌ی مستقل تقسیم می‌شود؛ هر
  پاره باید «تعداد جلسات در هفته» بار تشکیل شود.
- دروسِ تک‌جلسه‌ای هرگز در بازه‌های صبح قرار نمی‌گیرند.
- دروسِ دوجلسه‌ای باید هم‌ساعت، در یکی از دو الگوی (شنبه+دوشنبه) یا
  (یکشنبه+سه‌شنبه) جفت شوند — مگر این‌که داده یا در‌دسترس‌بودنِ استاد
  اجازه ندهد، که در این صورت به‌صورت fallback (بدون این الگوی خاص)
  زمان‌بندی و در پیام خروجی گزارش می‌شود.
- شیت «ارجحیت اساتید» دیگر ارجحیت نیست، بلکه **در‌دسترس‌بودن**
  (availability) است: جلسات هر استاد فقط می‌توانند در همان بازه‌هایی
  باشند که برایش ثبت شده. استادهایی که داده ندارند و کاربر در مرحله‌ی
  آپلود تایید کرده ادامه بدهد، در هر بازه‌ای آزادند.
- یک استاد یا یک کلاس نمی‌تواند هم‌زمان دو جلسه داشته باشد.

**محدودیت‌های نرم (در تابع هدف کمینه می‌شوند):**
- برای هر گروه دانشجویی، دو درسی که احتمال اخذشان «زیاد» یا «متوسط»
  است، تا حد امکان هم‌زمان نمی‌شوند.
- به‌طور اضافه، دو درسی که هر دو احتمال «زیاد» دارند، تا حد امکان
  همان روز و بدون فاصله پشت‌سرهم چیده می‌شوند (نه لزوما هم‌زمان
  اجتناب، بلکه چسبیده به هم) تا زمان حضور دانشجو در دانشگاه کم شود.
  این پاداش وزن کمتری از پرهیز از هم‌پوشانی دارد، پس هیچ‌وقت باعث
  هم‌زمان‌شدنِ دو درس نمی‌شود.

وزن‌های این دو محدودیت نرم (`GROUP_OVERLAP_PENALTY_WEIGHT` و
`CONSECUTIVE_BONUS_WEIGHT`) بالای همان فایل قابل تنظیم‌اند.

**چند گزینه به‌جای یک جواب:** به‌جای برگرداندن فقط یک چینش، solver
تلاش می‌کند تا ۳ چینشِ متفاوت از هم پیدا کند (نه لزوما هر سه هم‌ارزش
با بهینه — بهترین سه‌تای متمایزی که پیدا می‌شود؛ اگر داده اجازه‌ی
کمتر از ۳ تا بدهد، همان تعداد کمتر برگردانده می‌شود). کاربر در
فرانت‌اند یکی از این گزینه‌ها را انتخاب می‌کند و جدول/دانلود مخصوص
همان گزینه را می‌بیند؛ مسیر API مربوطه: `POST /api/schedule/solve`
آرایه‌ای از `options` برمی‌گرداند و `GET /api/schedule/download?option=N`
فایل اکسلِ همان گزینه‌ی مشخص را می‌دهد.

## نکته‌ی مهم — قبل از استفاده‌ی واقعی

نام شیت‌ها (`app/core/config.py`) و نام ستون‌های داخل هر شیت (در
`app/services/excel_reader.py`) بر اساس آخرین اطلاعاتی که داشتیم حدس
زده شده‌اند. **باید با فایل اکسلِ واقعیِ نهایی مقایسه و تنظیم شوند** —
این کار وقتی تمپلیت و داده‌ی نهایی آماده شد انجام می‌شود.

**فایل نمونه/تمپلیت دانلودی:** در صفحه‌ی آپلود یک لینک «دانلود نمونه
فایل اکسل» هست که از `frontend/public/schedule-template.xlsx` سرو
می‌شود. این فایل فعلا یک نسخه‌ی placeholder (بر اساس همان حدس‌های
اولیه) است. وقتی تمپلیت نهایی را آماده کردید، کافی است همین فایل را
با نسخه‌ی واقعی جایگزین کنید (نام فایل باید همان `schedule-template.xlsx`
بماند) — هیچ تغییر کدی لازم نیست.

## اجرا (توسعه‌ی محلی)

### بک‌اند
```
cd backend
pip install -r requirements.txt
uvicorn app.main:app --reload
```
سرور روی `http://localhost:8000` بالا می‌آید. مستندات تعاملی API در
`http://localhost:8000/docs` قابل مشاهده است.

**اولین اجرا — ساخت حساب مدیر:**
```
cd backend
python -m app.create_admin
```
ایمیل و رمز عبور مدیر را وارد کنید. بدون این مرحله، هیچ‌کس نمی‌تواند
کاربر دیگری را تایید کند (چون فقط مدیر به پنل مدیریت دسترسی دارد).

### فرانت‌اند
```
cd frontend
npm install
npm run dev
```
روی `http://localhost:5173` در دسترس خواهد بود.

## کنترل دسترسی (احراز هویت)

هرکسی که وارد سایت شود، ابتدا باید ثبت‌نام کند (ایمیل + رمز عبور).
حساب تازه‌ساخته‌شده تا وقتی مدیر آن را از پنل «مدیریت کاربران» (که
فقط برای حساب مدیر نمایش داده می‌شود) فعال نکند، اجازه‌ی ورود ندارد.
تمام مسیرهای اصلی برنامه (آپلود، حل مدل، دانلود) نیازمند ورود با یک
حساب فعال هستند.

قبل از استقرار نهایی حتما مقدار `jwt_secret_key` در
`backend/app/core/config.py` (یا از طریق فایل `.env`) را با یک مقدار
تصادفی و امن جایگزین کنید.

## استقرار (Deployment) — یک‌بار برای همیشه

این بخش یک راهنمای کامل برای بالا بردن دائمی سایت روی یک آدرس ثابت
است (با سرویس رایگان Render)، طوری که بعد از این مراحل دیگر هیچ‌وقت
لازم نباشد دستوری اجرا کنید یا کدی را لمس کنید — فقط آدرس را در
مرورگر باز می‌کنید.

پروژه از قبل برای این مسیر آماده شده:
- `backend/Dockerfile` — ایمیج بک‌اند را می‌سازد.
- `render.yaml` — یک «Blueprint» که هر دو سرویس (بک‌اند + فرانت‌اند) را
  با یک کلیک می‌سازد و متغیرهای محیطی لازم (JWT secret، CORS، آدرس
  API) را خودش تنظیم می‌کند.

چون سرویس‌های **پلن رایگان** Render نه دیسک دائمی دارند و نه دسترسی
Shell، دو تمهید دیگر هم در پروژه هست:
- دیتابیس باید یک Postgres **خارجی و رایگان** باشد (از سرویس Neon) —
  فقط با یک متغیر محیطی (`DATABASE_URL`) وصل می‌شود، نیاز به تغییر کد
  نیست.
- حساب مدیر با دو متغیر محیطی (`INITIAL_ADMIN_EMAIL` /
  `INITIAL_ADMIN_PASSWORD`) خودکار ساخته می‌شود؛ نیازی به اجرای دستی
  دستور نیست.

### مراحل (حدود ۱۵–۲۰ دقیقه، فقط یک‌بار)

۱. **ساخت ریپازیتوری روی گیت‌هاب** و آپلود کل پوشه‌ی پروژه (از
   «Add file → Upload files»).

۲. **ساخت حساب Render** با «Sign up with GitHub».

۳. **ساخت حساب Neon** (دیتابیس رایگان و دائمی):
   - به neon.tech بروید و با گیت‌هاب یا ایمیل ثبت‌نام کنید.
   - یک پروژه‌ی جدید بسازید (هر اسمی).
   - در صفحه‌ی داشبورد پروژه، دنبال **Connection string** بگردید —
     رشته‌ای شبیه `postgresql://user:password@ep-xxxx.neon.tech/dbname?sslmode=require`.
     آن را کپی کنید؛ در مرحله‌ی ۵ لازمش دارید.

۴. **ساخت Blueprint در Render**: «New +» → «Blueprint» → ریپازیتوری
   `scheduler-app` را انتخاب و «Connect» بزنید. اگر پیغام خطا درباره‌ی
   «disks are not supported for free tier» دیدید، یعنی نسخه‌ی قدیمی
   `render.yaml` را دارید — فایل `render.yaml` به‌روزشده را دوباره در
   گیت‌هاب آپلود کنید (جایگزین قبلی) و این مرحله را از اول بزنید.
   روی **Apply** بزنید و صبر کنید هر دو سرویس ساخته شوند.

۵. **وارد کردن متغیرهای محیطی بک‌اند**: در سرویس `scheduler-backend`
   → **Environment**:
   - مقدار `DATABASE_URL` را به همان Connection string که از Neon
     کپی کردید تغییر دهید.
   - مقدار `INITIAL_ADMIN_EMAIL` را به ایمیلی که می‌خواهید مدیر سایت
     باشد تنظیم کنید.
   - مقدار `INITIAL_ADMIN_PASSWORD` را به یک رمز عبور دلخواه تنظیم
     کنید.
   - **Save Changes** بزنید — سرویس خودش دوباره دیپلوی می‌شود و حساب
     مدیر را می‌سازد.

۶. **بررسی و اصلاح آدرس‌های متقابل (در صورت نیاز)**: آدرس هر سرویس را
   (چیزی شبیه `https://scheduler-backend-xxxx.onrender.com`) از بالای
   صفحه‌ی همان سرویس یادداشت کنید. اگر دقیقاً با چیزی که در
   `render.yaml` فرض شده بود فرق داشت:
   - در `scheduler-frontend` → Environment → `VITE_API_URL` را به
     آدرس واقعی بک‌اند تغییر دهید و Save کنید (دوباره دیپلوی می‌شود).
   - در `scheduler-backend` → Environment → `CORS_ORIGINS` را به آدرس
     واقعی فرانت‌اند تغییر دهید و Save کنید.

۷. **تمام.** آدرس فرانت‌اند را به‌عنوان نشانک ذخیره کنید و با همان
   ایمیل/رمزی که در مرحله‌ی ۵ تنظیم کردید وارد شوید.

**نکات مهم پلن رایگان:**
- سرویس بک‌اند بعد از ۱۵ دقیقه بی‌فعالیتی می‌خوابد؛ اولین درخواست بعدی
  حدود ۳۰–۵۰ ثانیه طول می‌کشد تا بیدار شود (فقط تأخیر است، نه خرابی).
  چون دیتابیس روی Neon است (نه روی خود سرویس)، این خواب‌ورفتن دیگر
  باعث پاک شدن حساب‌های کاربری نمی‌شود.
- دیتابیس رایگان Neon هم اگر مدتی بی‌استفاده بماند «می‌خوابد» و با
  اولین اتصال خودش بیدار می‌شود (چند ثانیه تأخیر، بدون پاک شدن داده).
- اگر در آینده خواستید این تأخیرها را حذف کنید، کافی‌ست پلن سرویس
  بک‌اند در Render را ارتقا دهید — نیازی به تغییر کد نیست.

وقتی قالب اکسل واقعی آماده شد، کافی است فایل
`frontend/public/schedule-template.xlsx` را با فایل واقعی جایگزین،
تغییرات را commit و push کنید — Render خودش به‌طور خودکار نسخه‌ی جدید
را دیپلوی می‌کند.
